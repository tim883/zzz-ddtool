# 当前输入与等待

核对日期：2026-10-12。本文描述现有代码。释放后等待设计见 [操作等待提速 Spec](../../dev-docs/功能改造/操作等待提速/Spec.md)（v9 已实施逐边下限）。

## 输入函数当前行为

源码为 [wininput.py](../../src/zzz_ddtool/wininput.py)。`pause` 用 `uniform` 选择请求睡眠时间；这些区间是代码常数，未证明是游戏最低需要时间。

| 输入 | 释放/发送之后的当前请求睡眠 |
| --- | --- |
| `click_client` | 普通点击鼠标释放后随机80—180 ms；Alt组合在鼠标释放与Alt释放之间另有40—80 ms，Alt释放后仍随机80—180 ms |
| `wheel_client` | 单条滚轮事件后固定150 ms，再随机80—180 ms |
| `press_key_once` | 最后一组KEYUP后固定30 ms，再随机350—550 ms |
| `press_key` | 现有多通道最后一次WM_KEYUP调用后随机450—650 ms |
| `send_wheel_event` | 单条原始滚轮，零内部收尾等待；调用者管理已标定的事件间隔 |

`focus_window` 每次先执行聚焦并等待200 ms，未成功再执行一轮并等待200 ms；释放前移动/按住间隔也仍存在。当前五类输入返回None，没有真实释放时间的返回接口。

`capture_inputs` 用ContextVar隔离输入观察，真实begin/end共享call_id，共16字段；初始检查点停止时不分配调用ID。输入结束事件在函数收尾等待之后记录，不能把end当作真实释放时刻。

## 业务等待当前行为

[gamefilter.py](../../src/zzz_ddtool/gamefilter.py) 在输入返回后还等待面板打开、重置、选项、滚动和确认。套装v8的layout等待字段为click=400、scroll=600、confirm=500 ms；面板打开550、重置450、号位120、主属性展开700、选项300 ms等固定值也仍执行。这些与输入内部等待是前后叠加关系。

[Runner._wait_ready](../../src/zzz_ddtool/runner.py) 的六类等待从输入函数正常返回后计时；当前默认下限/超时如下，适用的本机等待档案可调整下限。

| kind | 下限ms | 超时ms |
| --- | ---: | ---: |
| select_disc | 500 | 3000 |
| open_preview | 900 | 5000 |
| open_upgrade | 1500 | 8000 |
| material_ready | 600 | 3000 |
| upgrade_result | 1500 | 8000 |
| return_warehouse | 600 | 3000 |

`readiness` 当前predicate_version=1，生产poll=50 ms、连续稳定2帧。返回时刻口径的旧测量不能直接解释为“释放后游戏需要多久”。测量慢探针的下次调度已按抓图时刻计周期，不再在耗满周期后多睡50 ms；探针结束仍复核超时预算。

R/T由 `Runner._verify_label` 快速复核，输入返回后每次先等50 ms，最多 `max(1, preset.ocr_retry)*4` 次。只新帧重读，不补按；另一标签改变或一直未知时失败。弃置锁定盘先T确认解锁再R。返还确认的窗口/进程/尺寸、暂停代次和任务/盘面绑定保护已修复至真实输入检查点。

## 切页置顶的等待（2026-10-12）

[nav.py](../../src/zzz_ddtool/nav.py) 的 `_switch_tab` 原先在每次页签点击后固定 `sleep(1.1)`，两次点击合计硬等 2.2 秒，与页面是否真的切好无关。现在改为**认页驱动**：点完立刻抓图认页，认不出就继续重拍（每次点击最多 `max(1, ocr_retry)` 张，两轮之后仍认不出则存现场并抛 `NavError`）。切页成功那一刻即返回，动画未完成时由后续帧或下一次点击收敛。

这是页签切换的**就绪判据**，不是释放后等待，因此不进六类下限表；它也不参与 Spec v7 的动作全集与实测档案。`reset_to_top` 因此不再有固定等待，`_ensure_profile` 的短距标定沿用同一入口一并受益。改动对应 `tests/test_nav.py`（认页即返回、认不出重拍、两轮耗尽报错）。

## `return_warehouse` 逐边下限（2026-10-12）

`_esc_back_to_grid` 每次按 Esc 之前先认层，并用这次所在的边取等待下限（Spec v9 §12）。三条允许边各自一个值，互不牵连：

| 边 | 语义 | 运行时常量 ms |
| --- | --- | ---: |
| `modal_preview` | 弹层 → 缩放预览层 | 1680 |
| `modal_warehouse` | 弹层 → 仓库 | 1680 |
| `preview_warehouse` | 缩放预览层 → 仓库 | 680 |

改前三条边共用动作级一个值 1611 ms，于是 `preview_warehouse` 这类第 0 帧就 ready 的边也被拖到 1.6 s 以上；2026-10-12 真机一轮（`log/20261012-202521-215`）实测该动作 8 次合计 17.1 s，每件强化盘两次 Esc 约 4.3 s。现在快边按自己的下限走。

常量是**运行期兜底**，来自该轮运行时证据而非逐边真机实测；每边取得 ≥5 个有效样本后由档案 `return_edges`（`schema_version=2` 新增根字段）覆盖，取不到就回落到动作级兜底 1611 ms。判层判据、探针边判定、3580 ms timeout、两帧稳定与 50 ms poll 均未改动。`readiness.summarize_return_warehouse` 仍是标定/门禁侧的逐边汇总，本轮未改其合并口径。

## 筛选面板打开与「重置」（2026-10-12）

点漏斗按钮（`FILTER_BTN`）是**开/关切换**。面板本来就开着时（上一轮没关就点了开始），开头那一下会把它**关掉**，接着找「重置」读空、整轮中断。

**真机证据**：失败轮（`log/20261012-223608-951`、`log/20261012-230112-452`）的 `0002-导航到仓库.png` 左侧网格已被压暗（p95 119~129，面板开），而正常轮是 218~242（面板关）——说明任务开始时面板就是开着的。

现在 `_open_panel_and_reset()` 的做法：

1. 点一次漏斗 → 等 `open_panel` 下限 → 找「重置」（`FILTER_RESET_AREA` 内读「重置」、避开右侧「批量操作」）；
2. **找不到「重置」就再点一次漏斗**，再找一次。开关按两次回到原状态，所以面板原本开着会被恢复、原本关着则第一次就已经打开；
3. 仍未找到才抛 `FilterClickError`。

**代价**：面板本来关着（正常路径）仍是点 1 次漏斗 + 读 1 次区域 OCR，与旧实现相同，**不额外抓帧**；面板本来开着时多 1 次点击 + 1 次区域 OCR，但把"必然失败"救成"正常继续"。

**只用"读没读到重置"判断，不读亮度、不判面板开没开**——不依赖跨机器会变的像素阈值。`reset_game_filter` 传 `allow_reopen=False`：它读不到时紧接着就 Esc 关面板，没有"再点重置"的下一步，补点没有意义。

改动对应 `tests/test_gamefilter_reset_reopen.py`（正常路径只点一次、读不到补点一次、补点后仍失败则抛出、`reset_game_filter` 不补点）。

## 启动不再标定滚轮协议（2026-10-12）

`_ensure_profile` 原先在缺档时做完整标定，并**无条件**先跑一遍「打开筛选面板 → 重置 → Esc 关闭」；标定本身还会逐候选 `reset_to_top`（切页），并通过 `_verify_protocol` 验 4 组 × 2 遍（**每遍都 `reset_to_top`**）——**启动时最多 8 次来回切页**，每次后面还跟一次约 1200 ms 的大区域 OCR。

现在滚轮协议改用**出厂默认值**（`navigation.default_profile`）：

| 值 | 默认 | 来源 |
| --- | ---: | --- |
| `events_per_row` | 1 | 2026-10-02 真机标定 |
| `row_pitch_px` | 175 | 同上 |
| `event_interval_ms` | 100 | 同上 |
| `settle_wait_ms` | 100 | 同上 |

滚轮协议是**游戏规则常数**（滚动按行，1 条滚轮 = 1 行），不随筛选或列表长短变化，所以不必每次启动重测。`load_profile` 缺档/坏档/环境不匹配时**返回出厂默认值**（不再返回 `None`），启动直接进筛选页。用户档案 `user/navigation-profile.json` 命中时仍优先使用；`_ensure_profile(hwnd, recalibrate=True)` 保留为**显式重标定入口**（游戏更新改了滚动行为时用），那条路径才做"重置筛选 → 标定"。

`origin_center_y` **不在默认值之列**：它是"第 1 行图标中心的屏幕 y"，随当前滚到哪而变，每个任务开头仍由 `measure_layout` 按当前画面重新量，写死必然错位。

`_verify_protocol` 已随标定一并删除。改动对应 `tests/test_navigation.py`（缺档/坏档/环境不匹配均给出厂默认值）与 `tests/test_runner.py`（启动不标定、显式重标定仍先清筛选）。

## 「阶段添加」→「升级」改为固定间隔（2026-10-12）

`_upgrade_once` 原先在素材输入（点「阶段添加」）后做一次 `material_ready` 就绪等待：下限 947 ms，判据要求连续两帧读到「阶段添加」按钮、读到「升级」按钮、且素材条像素差分稳定；真机日志实测这一步让两次点击相隔 **1.00~2.00 秒**（`log/20261013-000950-544`，9 阶平均 1.78 s）。

作者裁定：**阶段添加后的动画不必等画面稳定**——直接点「升级」会让动画立刻结束，结果一样；素材是否到位也不用确认（点下去没反应会在后面的 `upgrade_result` 等待里超时暴露）。整个间隔要求 **≤500 ms**。

现在这一步只剩：

```
点「阶段添加」 → sleep _STAGE_ADD_TO_UPGRADE_S → 点「升级」硬编码中心
```

- **不再做 `material_ready` 等待**（生产路径已无该调用）
- **「升级」不再抓帧 + OCR 找文字**：改点 `UPGRADE_BUTTON_CENTER=(1511,866)`（设计坐标，`scale_point` 缩放）。真机日志里按 OCR 文字中心点出的是 `(1532,867)`，相差 21 px、同在按钮内。写法与「》」箭头（`scale_point(1416,226,...)`）一致。
- **间隔取值**：2026-10-12 先取 `0.1 s`；2026-10-13 作者一度裁定**取 0**（与 `substat_option`/`set_option` 的连点口径一致），真机验证通过后再裁定**取 `0.1 s` 作保险余量**。当前值 `_STAGE_ADD_TO_UPGRADE_S = 0.1`。
- **改前基准**：原 `material_ready` 等待使相邻两次点击的间隔中位约 **1.16 s**（`perf.jsonl` 实测，`log/20261013-003811-183` 一轮 7 阶）；改为固定间隔后这一步只剩「点击本身开销 + `_STAGE_ADD_TO_UPGRADE_S`」。
- 素材不足不再提前在这一步发现，而是在 `upgrade_result`（8180 ms 预算）里超时报错。

`material_ready` 这个动作 ID、它的探针与像素阈值**保留**：`_pick_material`（`material_slot>0` 的测试入口）仍消费它。生产路径已不触发。

改动对应 `tests/test_runner_waits.py::test_w2_stage_add_to_upgrade_uses_fixed_bounded_interval`（替代原 `test_w2_material_wait_starts_from_input_release`）与 `tests/test_runner.py` 的三条按钮用例。
