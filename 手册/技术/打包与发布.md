# 打包与发布（管理员手册）

> 面向**发版的人（老大）**。用户侧通过程序里的「检查更新」发起并确认更新。
> 更新：2026-10-13。发布入口改为 `scripts/release.py` 一条命令（每次固定含"生成示例清单"）；打包与检查更新接线已实施，历史打包/冒烟结果不代表本次重验；在线更新和干净机验收仍有缺口，发布按用户要求暂缓（见 [待办清单](../../dev-docs/待办清单.md)）。

---

## 0. 一句话

改内容 → 改版本号 → 提交 → `.\.venv\Scripts\python.exe scripts\release.py program` → 按打印的指引上传发行版。

`release.py` 是发布唯一入口：步骤固定、依次执行（生成示例清单 → 示例入库 → 打包 → 冒烟 → 打 zip → 推送 → 核对远端），任一步失败即停，修复后重跑同一条命令即可。只改公共示例或数据包时：`scripts\release.py examples` / `scripts\release.py data`。

## 1. 前置环境（一次性，两机通用）

- Python **3.13.5**（家用 / 工作统一，已定）。
- 在仓库根建隔离环境并装锁定依赖；已有正确 `.venv` 时只核对版本，不重复建环境：

```powershell
uv venv --python 3.13.5 .venv
uv pip install --python .venv\Scripts\python.exe -r requirements-lock.txt -e .
.\.venv\Scripts\python.exe --version
```

`requirements-lock.txt` 锁定运行和打包依赖版本（含 PyInstaller），便于两机对照。完整环境核对见 [开发与运行](开发与运行.md)；同步占位文件不代表解释器或依赖已可用。后续命令始终显式使用项目解释器。

## 2. 发一个版本

### 第 1 步：改内容 + 改版本号

| 改什么 | 改哪里 |
|------|------|
| 套装名 | `data/sets.json` |
| 词条名（OCR 词典 + 筛选主词条） | `data/stats.json` |
| 代码逻辑 | `src/zzz_ddtool/` |
| 版本号 | `pyproject.toml` 的 `version`（唯一来源） |

改完先提交：`program` / `data` 要求 `data/examples/` 之外的工作区干净（包内容必须与推送的提交一致），否则发布会在前置检查中止。

### 第 2 步：跑发布命令

```powershell
.\.venv\Scripts\python.exe scripts\release.py program
# 想在 dist/ 下保留历史包、每次发布独立目录：
.\.venv\Scripts\python.exe scripts\release.py program --outdir dist/发布-20261013
```

`release.py` 是发布唯一入口（要推仓库 = 跑它，见 `AGENTS.md`），步骤固定、依次执行，任一步失败即停并说明停在哪：

1. **前置检查**：`data/examples/` 之外的工作区必须干净——包内容是磁盘快照，必须与推送的提交一致；不干净会列出文件并中止。
2. **生成示例清单**：无条件重跑 `scripts/publish_examples.py`，清单永远跟着 `data/examples/` 走。
3. **示例入库**：`data/examples/` 下的未提交改动（示例 + 清单）随发布自动提交。
4. **打包**：`build.py`。产物 `<outdir>/zzz-ddtool/` = `zzz-ddtool.exe` + `_internal/` + `data/` + `version.txt`（`version.txt` 由 `build.py` 从 `pyproject.toml` 自动写入，两处永远一致）。默认 `--outdir` 为 `dist/发布-<当天日期>`，不会清空 `dist/` 下其他目录。
5. **冒烟**：`smoke_exe.py`（不触碰游戏）。
6. **打 zip**：`package_release.py --only program`（含 §3 全部校验；zip 根不套层）。
7. **推送**：`git push gitee <当前分支>`。
8. **核对远端**：`git ls-remote` 对比 hash，一致才算发布完成。

单独排查时可手动分步：

```powershell
.\.venv\Scripts\python.exe build.py --outdir dist/发布-20261013
.\.venv\Scripts\python.exe scripts\smoke_exe.py "dist\发布-20261013\zzz-ddtool\zzz-ddtool.exe"
.\.venv\Scripts\python.exe scripts\package_release.py --pkg "dist\发布-20261013\zzz-ddtool" --outdir "dist\发布-20261013"
```

- `--outdir` 是包的**父目录**。脚本在任何删除前验证包目录和 `build/`，拒绝与源码/用户目录重叠、包或中间目录经链接转向其他位置，以及清理目标含源码或用户数据标记的情况。误填 `--outdir ..` 会退出并保留文件。
- 历史打包记录：onedir 约 **328MB**，RapidOCR 模型随包带全；每次发布按实际产物核对大小和资源。

### 第 3 步：传 Gitee 发行版

第 2 步的命令已经打出 zip。**两个包，按需发：**

| 包 | 什么时候发 | 内容 | 命名（必须先看这条） |
|---|---|---|---|
| **数据包** | 只改了外置套装名 / 词条名 | `data/` 里的运行资源 | 以 `data` 开头，如 `data.zip` |
| **程序包** | 改了代码 | 整个程序目录内容 | 其余任意名，如 `zzz-ddtool-v0.2.0.zip` |

程序按**文件名**识别：`data*.zip` = 数据包，其余 `.zip` = 程序包。

单独打 zip（不走完整发布流程时）：

```powershell
# 与上面的独立输出目录对应；用默认输出时去掉 --pkg。
.\.venv\Scripts\python.exe scripts\package_release.py --pkg "dist\发布-20261013\zzz-ddtool" --outdir "dist\发布-20261013"
```

脚本产出两个 zip，语义与上表一致：

| 产出 | zip 根的内容 |
|---|---|
| `zzz-ddtool-v<版本>.zip` | 程序目录里的内容 |
| `data.zip` | `data/` 里的内容 |

只出一种时加 `--only program` 或 `--only data`。

**出包前会校验，任一条不满足就中止、且不产出任何 zip**：包目录必须存在且含 `zzz-ddtool.exe` / `_internal/` / `data/` / `version.txt`；**顶层不得有 `user/`、`log/` 或 `log_test/`**；`version.txt` 必须与 `pyproject.toml` 一致。

使用刚打出的未运行产物打 zip；交付包不包含 `user/`、`log/`、`log_test/`，也不包含 `data/` **直属**的任务 YAML —— 但 `data/examples/` 下的随包示例**要发**（它是给首次使用者用的发布资源）。程序更新器会覆盖程序包中的文件，不能把个人存档放入发布附件。

> ⚠️ **关键坑：zip 不能多套一层目录。**
> 解压后**根目录必须直接是目标内容**：
> - 数据包根 = `sets.json` / `stats.json` / ...
> - 程序包根 = `zzz-ddtool.exe` / `_internal/` / `data/` / `version.txt`
> 多套一层（如 zip 里是 `zzz-ddtool/xxx`）会导致解压错位。脚本已按此产出并有测试钉住；若绕过脚本手工打 zip，这条要自己保证。

## 3. 传到 Gitee 发行版

仓库：`qzl2077/zzz-ddtool`。

**网页操作**（推荐，简单）：

1. 打开仓库 → 右侧「发行版 / Releases」→「新建发行版」。
2. 填 **标签（tag）= 版本号**，如 `v0.2.0`（带不带 `v` 都行，程序会自动去掉）。
3. 填标题 + **更新说明**（这个说明会原样显示给用户看，写清楚改了什么）。
4. 上传上一步的 zip 附件。
5. 发布。

发布流程 3 步（对应你要的"发个版本"）：
1. 打 zip；
2. 传发行版附件；
3. 填版本号 + 说明。

## 4. 用户侧更新时发生什么

| 情形 | 用户看到 | 程序行为 |
|---|---|---|
| 有程序包 | "发现新版本 X，现在更新？" | 下载 → 退出 → 替身 bat 覆盖 → 重启新 exe |
| 只有数据包 | "发现新版本 X，现在更新？" | 下载 → 覆盖 `data/` → **立即生效、不重启** |
| 已是最新 | "已是最新版本 X" | 无动作 |
| 无网络 / 无发行版 | 对应错误提示 | 无动作 |

数据更新覆盖 `data/`；程序更新覆盖程序目录中的包内文件。本流程的发布包不包含 `user/`，存档位置见 [开发与运行](开发与运行.md)。**日志与 `user/` 同一条定位规则，落在公共根 `log/`，不在版本目录内**——换版本目录不会丢掉旧日志。当前更新器没有覆盖前备份或失败回滚。**更新器另有一层剥离**：解压后、覆盖前会删掉更新包里顶层的 `user/`、`log/` 与 `log_test/`，即使发布包出了错，用户侧也不会被覆盖。

## 5. 端到端验证（发版后自查）

1. 拿**上一个版本**的 exe（或把 `version.txt` 临时改小）。
2. 点「检查更新」→ 应提示新版本 → 确认。
3. 数据更新：确认 `data/` 被替换、`user/plan/` 与 `user/last-config.json` 没动。
4. 程序更新：确认退出后自动重启、版本号变成新的。

## 7. 更新公共示例（不用发版）

示例与清单直接放在本仓库 `data/examples/`，用户从界面「获取公共示例」按需下载。

```powershell
# 改完 data/examples/ 里的示例后，一条命令完成：生成清单 → 入库 → 推送
.\.venv\Scripts\python.exe scripts\release.py examples
```

- **生成清单不是独立动作，而是发布流程的固定步骤**——`release.py` 每次都跑它，控制 `data/examples/` 就等于控制发版，不存在"忘了重生成清单"的窗口。
- 清单里的 `note` 是界面上显示的说明，**手写，重新生成时按文件名保留**。
- 用户侧会逐个核对 `sha256`，与清单不符的一律拒绝落盘。
- 改了示例**不必**重打程序包，也不必发发行版 —— 推一下仓库即可。

## 8. 对照：改动 → 发什么包

| 你改了什么 | 发哪个包 | 用户侧动作 |
|---|---|---|
| 套装名 / 词条名 | 数据包（几 KB） | 点更新 → 立即生效 |
| 任何代码 / 内置模板资源 | 程序包（大小以当次产物为准） | 点更新 → 退出重启 |
| 公共示例（`data/examples/`） | 不发包，`release.py examples` 推仓库 | 「获取公共示例」按需下载 |
