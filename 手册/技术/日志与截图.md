# 日志与截图规范

> **本文只规范运行日志截图。开发参考截图另存 `手册/参考图/`，长期维护、不参与本页的日志清理；参见 [参考截图索引](../参考图/索引.md)。** 调试图经核对和登记后可复制入库，两者保持独立生命周期。

出问题时能回答三件事：**第几步、在哪个页面、当时屏幕上是什么**。

## 一、为什么一步一扫

这是 **OCR + 模拟点击**工具。不 OCR 就不知道现在在哪个页面、按钮在不在、
坐标有没有偏。截图是唯一能事后核对「当时屏幕长什么样」的东西。

**一步一扫是基础，不是可选的高级功能。**

现在已经在省的地方（整页扫一次出清单、点格子用清单坐标直接点）保持不动，
后续想到了再针对性省 OCR——**先做准，再提速**。

## 二、日志格式

统一「**在哪个页面 · 干了什么 → 结果**」，全中文：

```
17:03:41 [信息] 驱动盘仓库 · 导航到仓库 → 成功（已到驱动盘仓库）  截图=0001-导航到仓库.png
17:03:42 [信息] 详情页 · 点开格子 → 成功（第 1 个/共 9 个 · 第2行第3列）  截图=0004-点开格子.png
17:03:42 [信息] 详情页 · 识别盘面 → 成功（第 1 个 等级3 副词条4条）  截图=0005-识别盘面.png
17:03:42 [信息] 详情页 · 判断     → 结论（继续强化：分数4.0≥要求3.5）
17:03:46 [错误] 详情页 · 进强化页 → 失败：没找到「查看」按钮  截图=0025-进强化页.png
```

- 页面中文名在 `trace.py::PAGE_NAMES`，动作中文名在 `ACTION_NAMES`
- 认不出的页面/动作**原样输出，不编名字**——编了会误导排查
- 判断类动作结果写「结论」，不写「成功」（"判断 → 成功"读着别扭）
- **判断不截图**：它是纯计算，不碰屏幕，截出来跟上一张一模一样
- 「截图=」后面是**本轮 `captures/` 里的文件名**，前缀就是步骤号

## 三、截图从哪来

不重复抓、不重复 OCR：

| 这一步 | 图从哪来 |
|--------|----------|
| 做了 OCR | 调用方把那张图传进来（`image=xxx`）直接存盘。抓图+推理开销已付，写盘只多几毫秒 |
| 没做 OCR（点格子、按 R、Esc、滚轮） | 现截一张。**这类步骤正是坐标可能偏的地方**，图是核对坐标的唯一依据 |

代码里就是 `trace.ok(page, action, detail, image=...)`——传了就用，没传就现截。

## 四、容量怎么控（按轮数整轮回收）

截图 1.5MB 一张，不控会撑爆磁盘。**保留单位是一轮**：超了从最旧的**轮次目录整轮删**，
主日志、报告、统计、性能、截图和诊断一起走——半截的轮次没有参考价值。

- 默认保留最近 **5 轮**，窗口「日志设置」里可以改，范围 **1—100 轮**。
- **正在写入的那一轮不占名额**，所以运行期间目录数可能暂时多于设置值，收尾后收敛。
- 成功、失败、素材不足、主动停止的轮次用同一套规则；**失败不永久保留**。
- 不看 INFO/DEBUG 级别、也不看这一轮有没有真的点过游戏。

不做的三件事：

- **不做「失败永远保留」**：排错靠 debug 模式重跑复现，不靠翻旧图回溯。
  留着失败图只会把正常的挤掉。
- **不按容量 / 天数**：截图大小会浮动，按容量用户没法预期能留多久。
  只限轮数就意味着占用随单轮规模变化，不承诺固定的 MiB 上限。
- **不做第二套开发日志的保留设置**：`log_test/` 由开发者自己管。

什么时候会试着回收：程序启动后、任务收尾后、切到下一轮、退出程序、改完保留轮数。
删不掉的目录留在原地并记一条原因，下次触发重试；**清理失败不影响任务结果**，
失败项也不计入已回收数量。

## 五、目录与命名

**一轮 = 一个时间戳目录**，正式运行的产出都在里面：

| 路径 | 内容 |
|------|------|
| `log/run-status.json` | 运行状态指针（界面每秒读一次），留在日志根上，不随轮次回收 |
| `log/<时间戳编号>/round.json` | 轮次登记：格式版本、来源、启动/结束时间、结束结果、产物相对路径 |
| `log/<时间戳编号>/ddtool.log` | **本轮文本日志**，一轮一个文件，不分卷 |
| `log/<时间戳编号>/report.md` | 执行结果总结（界面「详细结果统计」点开的就是它） |
| `log/<时间戳编号>/stats.json` | 结构化统计 |
| `log/<时间戳编号>/perf.jsonl` | 本轮性能区间、实际输入及决策证据 |
| `log/<时间戳编号>/captures/` | 本轮步骤截图 |
| `log/<时间戳编号>/success/` | 升满保留的成功盘图 |
| `log/<时间戳编号>/diagnostics/` | 故障取证（详细级别下的套装拒绝原帧等），按需产生 |
| `log_test/<时间戳编号>/` | 测试、探测、回放、标定、基准和验证脚本的日志根，结构与 `log/` 相同 |
| `log_test/legacy/<迁移时间戳>/` | 改造前旧布局的归档，**不参加自动回收** |

目录编号形如 `20261012-153012-047`：本机本地时间 + 三位毫秒。同一毫秒撞名会重新取时间，
用原子建目录保证不复用、不覆盖已有目录。文件名和子目录按实际产物创建，
**不生成空报告、空性能文件或占位截图**。

`log/` 与 `log_test/` 的位置与 `user/` **同一条规则**：开发态 = 仓库根，打包态 = 公共根
（从 exe 同级向上找 `.zzz-ddtool-root`，没有标记时回退到 exe 同级）——所以把包放进新版本目录、
删掉旧版本目录，旧日志仍在。这不包括长期保存的开发参考图 `手册/参考图/`。

测试与开发入口（pytest、`capture`/`read-disc`/`goto-warehouse`/`snapshot-pages`/`snapshot-list`/
`preview`、`--start-index`/`--material-slot` 非默认的 `run`、`scripts/` 下的探测与标定脚本）
写 `log_test/`；正常 `run` 与界面启动写 `log/`。归属不看日志级别，也不看进程有没有发输入。

图片命名：`0007-进强化页.png`——**前缀就是步骤号，和文本日志那一行对得上**。

性能证据由 `Runner.run` 开启并收尾，`run_total` 保存实际任务配置、准备/处理区间与输入；
`disc_total` 保存完整盘面决策、输入及其等待/后置结果。输入观察器直接记录 `wininput` 的
begin/end，begin 只代表调用开始，不能当作按键已经发出；标签输入正常完成而复核失败时仍保留输入
及失败结果。`runevidence.py` 从原始事件生成报告并核对关联，最终门禁另读实际 YAML 核对名单和
配额。报告删空或引用不存在的输入不能通过，旧记录缺少字段时判不完整，不补造历史证据。
父子性能区间有重叠，不相加估算总耗时。

## 六、排查流程

1. 打开**当前轮次**的 `ddtool.log`（界面顶部「日志文件」那一行就是当前轮次的路径）
2. 找 `[错误]` 那行
3. 看行首步骤号，比如 `0025`
4. 去同目录 `captures/0025-*.png` 看当时屏幕
5. 往上翻十几行，看是怎么走到这的
6. **要复现就开「详细」级别重跑**——别指望靠翻旧日志定位

历史轮次被清理后，界面上的结果统计会显示「该轮报告已回收」，不再给指向不存在文件的链接。

## 七、强化统计口径（2026-10-07）

`<轮次>/stats.json` 的阶段 `seconds` 从本档阶段添加/测试材料操作之前开始，
到新盘面确认达到期望等级为止；素材不足则到有限重试耗尽。包含本档按钮定位、输入、
等待和结果识别，不包含进入强化页的导航。旧运行 JSON 不重写；早期版本在升级操作
返回之后打点，不能把旧阶段耗时直接与新完整区间比较。

按实际到达等级分别列桶，例如阶段添加使 0 级到 4 级时，JSON、Markdown 与日志显示独立 4 级，
不归到 3 级。空报告仍保留 3/6/9/12/15 固定档位。总览“扫描跳过”是网格跳过格位；
结果明细“进入处理后跳过”是已经读过盘面的结果，两者范围不同。

长动作是真实区间，步骤统计是两次日志事件间隔，二者重叠，不相加。DEBUG 取证也占本轮墙钟时间；
降低 OCR 后的实际速度需用新客户端真机验证。

## 八、查「重复抓图 / 重复 OCR」（详细级别）

**详细级别**下有三个埋点，专门回答"这里是不是多抓/多读了"：

| 埋点 | 落在 | 看什么 |
|------|------|--------|
| `capture.grab_game_image` | 本轮 `ddtool.log` | 每次截屏都记一行：尺寸、`hwnd`。**同一步里连出两行 = 多抓了一帧** |
| `ocr.read_rect` | 同上 | 每次 OCR 记一行：区域、行数、图尺寸、耗时、`image.cacheKey()`。**同一 `cacheKey` 出现两次 = 同一帧读了两遍** |
| `screen.classify_image` | 同上 | 认页结果（模板命中 / 启发式兜底），用来确认某一帧到底停在哪个页面 |

> **级别是过滤器，不是探针**：代码里没写日志语句的地方，开到详细也不会多出记录。
> 这三个埋点是**唯一收口**——别指望在别处也能看到抓图和 OCR。

`image.cacheKey()` 是关键：它是 Qt 给同一张图分配的标识，同一帧反复 OCR 会显示同一个值。
排查"多读了"就看它，不用靠肉眼比对时间戳。

## 八之二、一轮结果一键分析（`scripts/analyze_round.py`）

每轮统计报告（`report.md`）只给动作级汇总；**逐边等待、切页墙钟、同帧重复读取**这三类
需要按输入事件和 probe 样本折算。用仓库脚本一次产出，不手抄数字：

```powershell
# 最新一轮
.\.venv\Scripts\python.exe scripts\analyze_round.py --latest
# 指定轮次
.\.venv\Scripts\python.exe scripts\analyze_round.py --round log/<时间戳编号>
```

脚本只读 `log/<轮次>/` 下的 `perf.jsonl`、`ddtool.log`、`round.json`，不操作游戏、
不改动运行数据；退出码 0 = 正常，2 = 轮次/文件缺失。它给出四段：

1. **`return_warehouse` 逐边**：每次 Esc 属哪条边（由 probe 样本 `state_key` 的
   before→after 反推）、实际等待、下限值、探针次数、首帧是否已 ready。**首帧 ready
   却仍等满下限 = 在凑下限**，这是可以继续压缩的部分；就绪本身慢则下限不是主因。
2. **切页置顶墙钟**：恢复阶段页签点击的实际单次耗时，用来确认没有固定等待残留。
3. **同帧重复读取**：从 `ddtool.log` 的「识别 …图#<帧标识>」比对同一帧同一区域是否
   被读两次。判定只看恢复路径的两个区域——标题数量 `(60,105,420,175)` 与恢复列
   `(100,200,230,945)`；预览层等级区 `(1140,175,1420,265)` 的重拍属 Esc 等待的预期
   行为，单列出来不混算。
4. **动作耗时与抓图总量**：按 `kind` 汇总实际输入，便于和 `report.md` 对照。

口径说明与逐边常量见 [输入与等待](./输入与等待.md)、[等待时间表](../../dev-docs/功能改造/操作等待提速/等待时间表.md)。

**跑完要盯的异常**：切页单次点击若明显变慢、或日志出现 `切页 …切换失败`，说明去掉固定等待太急；`modal_preview` 若出现首帧 ready 而历史是 0/N，说明判层提前命中，需查误判；`preview_warehouse` 若仍停在 1.6 s 以上，说明逐边下限没生效（查档案里是否被写进了动作级 `policies["return_warehouse"]`）。

## 九、加新步骤

在 `runner.py` 里调用 `self.trace`：

```python
self.trace.new_disc()                                    # 开始处理一个新盘
self.trace.ok("detail", "parse", f"等级{disc.level}", image=img)  # 成功，传 OCR 那张图
self.trace.fail("detail", "enter_upgrade", "没找到按钮", image=img)  # 失败，图必留
self.trace.warn("detail", "parse", "没读出盘面", image=img)          # 可疑，图必留
self.trace.note("补充说明，不算一步")                      # 注释
```

- 第一个参数是页面标识，第二个是动作名
- 不在映射表里会原样输出，**加新页面/动作时记得去 `trace.py` 补中文名**
- 开始处理新盘时调一次 `new_disc()`，盘号决定这批图最后留不留

## 十、级别与轮数在哪改

窗口顶部「**日志设置**」按钮，或者命令行：

```powershell
.\.venv\Scripts\python.exe -m zzz_ddtool -v run --config user/plan/example.yaml
```

`-v` 等于级别调到「详细」（额外打步骤号），平时不用开。

设置窗口里改的两项（级别、历史日志保留轮数）**会记住**——存到 `user/log-settings.json`，
下次启动自动装回；命令行 `-v` 只对那一次运行生效。

设置窗口里能改：

| 项 | 说明 |
|----|------|
| 日志级别 | 常规 / 详细 / 只看问题。**截图始终全量，不受级别影响** |
| 历史日志保留最近 | 文本框，1—100 轮，默认 5。超了从最旧的轮次整轮删，正在写入的一轮不占名额 |
| 当前轮次 / 历史轮数 / 占用 | 显示当前正在写的轮次、可回收的历史轮数和日志根占用，填上限时有依据 |
| 打开当前日志文件夹 | 直接开当前轮次目录 |
| 打开日志根目录 | 开 `log/` 根，看所有轮次 |
| 清理历史日志 | 只清已关闭的历史轮次，保留正在写入的目录；返回实际删掉的轮数 |

旧版本配置里只有「截图最多留 N 张」，与轮数不是一个量纲：读不出来就按默认 5 轮处理，
保存时写成新格式（`version` + `max_rounds`）。
