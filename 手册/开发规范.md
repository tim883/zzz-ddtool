# 开发规范

更新：2026-10-05。适用于本仓库及协作 agent。**仓库内文档统一在 `手册/`，开发参考图连同游戏规则解释统一在 `手册/参考图/`；日志图片不充当长期开发参照。**

## 1. 固定入口和存放位置

| 内容 | 唯一维护位置 |
| --- | --- |
| 文档总入口 / agent 自动发现入口 | [手册目录](目录.md) / 仓库根 `AGENTS.md` |
| 项目开发规范 | 本文；不在多个目录维护全文副本 |
| 已确认的游戏前提 | [游戏规则](./游戏规则.md)；页面图说明引用相应规则 |
| 用户怎么操作现有工具 | `手册/使用/` |
| 已实现的技术机制、坐标和识别方法 | `手册/技术/` |
| 长期参考图与逐页解释 | `手册/参考图/<页面名>/`，从 [图库索引](参考图/索引.md) 进入 |
| 改造 spec / plan / review、协作与验证记录 | `dev-docs/`；每个改造在同一主题目录维护和索引 |
| 程序实际加载的识别模板 | `src/zzz_ddtool/assets/templates/`，属于运行资源 |
| 回归专用输入 | `tests/fixtures/`；可直接复用参考图，不要求复制一份 |
| 当次运行日志 / 临时探测图 | `log/`，不进 git，按日志策略清理 |
| 用户任务存档 | `user/plan/`；不放 AppData，不随版本包搬迁 |

`dev-docs/` 与 `手册/` 同在一个仓库，职责不同：前者承载改造过程资料，后者是长期规范。只拿到源码仓库的 agent 也能从本文和游戏规则了解开发前提。需要具体改造方案而对应文件不存在时应明确缺失，不能从审查报告自行拼出需求。

根 `README.md` 是项目首页，详细文档只有一套。手册目录命名为 `目录.md`，图库入口命名为 `索引.md`，页面解释命名为 `说明.md`，不要再把同一段项目介绍复制到各级 README。

## 2. 两种截图不能混用生命周期

**参考图**是写代码时可反复引用的资产，放 `手册/参考图/`，纳入源码版本管理，不参加日志清理，不作为用户运行包资源。**运行图**是某轮任务的步骤或故障证据，放 `log/captures/<轮次>/`，和日志对应，可能被回收。

调试可以查看日志图；要长期作为改造依据，先把适用原图复制到参考图库，配上说明，再让 spec、技术文档或测试引用入库路径。保留日志来源用于追溯，但不能只给一个日志时间戳让后续 agent 自己猜游戏规律。不要把每轮图片自动灌入图库，也不要为归档增加正式任务中的额外操作。

**本次规范不要求为已经完成且不改动的功能追补图片。** 新功能或现有功能改造只维护本次涉及、足以解释行为的必要样本；优先复用已有图。没有采集日期 / DPI 等历史元数据时标“未记录”，不能据此把已完成功能重新列为阻塞待办。

## 3. 图片必须配游戏语义说明

每个页面目录用一份 `说明.md` 解释：

1. 图片在哪、哪个页面 / 状态、实际尺寸；截图的来源与已知筛选条件。
2. **画面元素意味着什么、哪些游戏规则已经由用户确认、操作之后会发生什么、这些规则如何影响实现。** 用户确认直接登记为前提，无需接手者重新问用户。
3. 哪些结论仅是静态外观、哪些规则来自操作观察、哪些代码已经实现、哪些功能尚在设计。具体颜色阈值和实现验收不由静态图片代替。
4. 与技术文档、功能 spec 或现有测试的关联；仅记录与本次改造有关的真实缺口。

保存客户区实际图像，PNG 无损；1920×1080 是设计坐标基准，不拉伸历史图冒充原生。原图不涂改，裁剪或标注放该页 `裁剪/` 或另命名并说明来源。配对图片按“操作前 / 后”和操作内容说明；无法从单图推出动态机制时，引用已有规则记录，不能临时编造。

规则集中维护在 [游戏规则](./游戏规则.md)，页面说明用规则编号引用，避免几份文档互相改出矛盾。同一张图同时用于用户讲解、开发和测试时共用路径。运行模板用途不同，保留在源码资源中；图库里的历史裁剪仅作解释，不让程序改成从手册加载。

## 4. 文档维护流程

- 开始改造：读本文、游戏规则及对应页面说明，再读该改造 spec。已有已确认前提直接使用，有新证据冲突才指出冲突并讨论。
- 实现期间：更新本次相关参考样本和说明；代码变化同步修订技术文档。spec 的“尚未实施”不能被使用说明当作已实现。
- 完成时：核对链接、图片加载、受文件移动影响的既有回归；分别记录代码、离线测试、真机验证的结果。证据不足写具体缺口，不泛称整项功能未完成。
- 不另建 `doc/`、`docs/`、`screens/`；不复制核心规范到 `dev-docs`。历史材料引用旧路径时通过迁移记录解释，不继续创建重复目录。
- 用户最新明确要求优先。审查报告只记录意见；环境报告和测试数量只代表对应日期，不自动变成今日事实。

测试报告说明验证对象与限制，不以通过数量代替功能结论。停用功能或标定集上的函数测试不能当作当前执行链 / 独立真机验收；固定归档图片缺失应失败，不能静默跳过。涉及三态识别的测试须保留未知，不能把未知当作空位或成功。过时或不再有验证价值的用例可修订或删除，不为维持数量而保留。

## 5. 延续的开发约束

- 本地截图 / OCR / 模拟输入；弃置仅打标，不分解、不读游戏内存、不改游戏文件、不抓包。
- 强化按 +3 档重新判断；初始 3 / 4 词区分处理。任务 `accepted=None` 表示未生成而跳过；空白名单 `[]` 是有效配置，不回退到权重接受。
- F9 暂停 / 恢复、F10 停止与 GUI 共用控制器；任务后台执行、界面响应，关闭先请求停止。未知情况无法可靠继续时有限重试后停止整条链，失败不能显示完成。
- 列表定位按批复用，不为了补参考图改成每盘重扫、每行截图。仓库位置、端点和恢复判定完全不用滑块，包括辅助和兜底。
- 开发 / 打包目标 Python **3.13.5**，显式使用项目 `.venv\Scripts\python.exe` 和锁定依赖；包元数据 `>=3.11` 不是两机可以混用版本的约定。环境、DPI 和滚轮协议本机核对，不凭历史文档修改全局环境。
- 目录整理保留图片内容、运行模板、既有功能与用户存档；阶段完成后另行打包并保留旧包。
