# 打包与发布

面向负责发版的人。用户侧通过程序里的「检查更新」发起并确认更新。打包与发布入口都已接好；剩余事项（在线更新端到端验证、干净机验收等）维护在源码根同级的私有开发资料目录中，不随公开仓库提交，完成后把现行结论整理进本文。

---

## 0. 一句话

改内容 → 改版本号 → 提交 → `.\.venv\Scripts\python.exe scripts\release.py program` → 按打印的指引上传发行版。

`release.py` 是发布唯一入口：`program` / `data` 场景步骤固定、依次执行（前置检查 → 生成示例清单 → 示例入库 → 打包 → 冒烟 → 打 zip → 推送 → 核对远端），任一步失败即停，修复后重跑同一条命令即可；`examples` 场景只到「推送」为止，不打包、不冒烟、不出 zip。三种场景都用 `scripts\release.py examples|program|data` 触发。加 `--dry-run` 只打印将执行的步骤与检查结果，不写入任何东西。

## 1. 前置环境（一次性，两机通用）

- Python **3.13.5**（家用 / 工作统一）。
- 在仓库根建隔离环境并装锁定依赖；已有正确的 `.venv` 时只核对版本，不重复建环境：

```powershell
uv venv --python 3.13.5 .venv
uv pip install --python .venv\Scripts\python.exe -r requirements-lock.txt -e .
.\.venv\Scripts\python.exe --version
```

`requirements-lock.txt` 锁定运行和打包依赖版本（含 PyInstaller），便于两机对照。完整环境核对见 [开发与运行](开发与运行.md)；后续命令始终显式使用项目解释器。

## 2. 发一个版本

### 第 1 步：改内容 + 改版本号

| 改什么 | 改哪里 |
|------|------|
| 套装名 | `data/sets.json` |
| 词条名（OCR 词典 + 筛选主词条） | `data/stats.json` |
| 代码逻辑 | `src/zzz_ddtool/` |
| 版本号 | `pyproject.toml` 的 `version` 与 `src/zzz_ddtool/version.py` 的 `FALLBACK_VERSION`（两处须一致） |

改完先提交：`program` / `data` 要求 `data/examples/` 之外的工作区干净（包内容是磁盘快照，必须与推送的提交一致），否则发布会在前置检查中止。

### 第 2 步：跑发布命令

```powershell
.\.venv\Scripts\python.exe scripts\release.py program
# 想在 dist/ 下保留历史包、每次发布独立目录：
.\.venv\Scripts\python.exe scripts\release.py program --outdir dist/发布-YYYYMMDD
```

`release.py` 是发布唯一入口（要推仓库 = 跑它，见仓库根 `AGENTS.md`），步骤固定、依次执行，任一步失败即停并说明停在哪：

1. **前置检查**：`data/examples/` 之外的工作区必须干净——包内容是磁盘快照，必须与推送的提交一致；不干净会列出文件并中止。
2. **生成示例清单**：无条件重跑 `scripts/publish_examples.py`，清单永远跟着 `data/examples/` 走。
3. **示例入库**：`data/examples/` 下的未提交改动（示例 + 清单）随发布自动提交。
4. **打包**：`build.py`。产物 `<outdir>/zzz-ddtool/` = `zzz-ddtool.exe` + `_internal/` + `data/` + `version.txt`（`version.txt` 由 `build.py` 从 `pyproject.toml` 自动写入，两处永远一致）。`release.py` 不传 `--outdir` 时用 `dist/发布-<当天日期>`（上面的 `YYYYMMDD` 换成当天日期）；单独跑 `build.py` 时它自己的默认 `--outdir` 是 `dist`，产物 `dist/zzz-ddtool/`。不会清空 `dist/` 下其他目录。
5. **冒烟**：`smoke_exe.py`（不触碰游戏）。
6. **打 zip**：`package_release.py --only program`（含下文全部校验；zip 根不套层）。
7. **推送**：`git push github <当前分支>`。
8. **核对远端**：`git ls-remote` 对比 hash，一致才算发布完成。

单独排查时可手动分步：

```powershell
.\.venv\Scripts\python.exe build.py --outdir dist/发布-YYYYMMDD
.\.venv\Scripts\python.exe scripts\smoke_exe.py "dist\发布-YYYYMMDD\zzz-ddtool\zzz-ddtool.exe"
.\.venv\Scripts\python.exe scripts\package_release.py --pkg "dist\发布-YYYYMMDD\zzz-ddtool" --outdir "dist\发布-YYYYMMDD"
```

- `--outdir` 是包的**父目录**，产物目录名固定为 `zzz-ddtool`（由 `zzz-ddtool.spec` 的 `COLLECT name` 决定）。
- 打包只清理本次目标目录与 `build/` 中间目录，`dist/` 下的历史包一律不动。
- 打包产物含完整 RapidOCR 模型，`_internal/` 体积较大；每次发布按实际产物核对大小和资源。

### 第 3 步：传 GitHub 发行版

第 2 步的命令已经打出 zip。**两个包，按需发：**

| 包 | 什么时候发 | 内容 | 命名（必须先看这条） |
|---|---|---|---|
| **数据包** | 只改了外置套装名 / 词条名 | `data/` 里的运行资源 | 以 `data` 开头，如 `data.zip` |
| **程序包** | 改了代码 | 整个程序目录内容 | 其余任意名，如 `zzz-ddtool-v<版本>.zip` |

程序按**文件名**识别：`data*.zip` = 数据包，其余 `.zip` = 程序包。

单独打 zip（不走完整发布流程时）：

```powershell
# 用默认输出目录打包时，--outdir 可以省略（默认 = 包目录的父目录）。
.\.venv\Scripts\python.exe scripts\package_release.py --pkg "dist\发布-YYYYMMDD\zzz-ddtool"
```

脚本产出两个 zip，语义与上表一致：

| 产出 | zip 根的内容 |
|---|---|
| `zzz-ddtool-v<版本>.zip` | 程序目录里的内容 |
| `data.zip` | `data/` 里的内容 |

只出一种时加 `--only program` 或 `--only data`。

**出包前会校验，任一条不满足就中止、且不产出任何 zip**：包目录必须存在且含 `zzz-ddtool.exe` / `_internal/` / `data/` / `version.txt`；**顶层不得有 `user/`、`log/` 或 `log_test/`**；`version.txt` 必须与 `pyproject.toml` 一致。

使用刚打出的未运行产物打 zip；交付包不包含 `user/`、`log/`、`log_test/`，也不包含 `data/` **直属**的任务 YAML —— 但 `data/examples/` 下的随包示例**要发**（它是给首次使用者用的发布资源）。程序更新器会覆盖程序包中的文件，不能把个人存档放入发布附件。

> ⚠️ **关键坑：zip 不能多套一层目录。**
> 解压后**根目录必须直接是目标内容**：
> - 数据包根 = `sets.json` / `stats.json` / ...
> - 程序包根 = `zzz-ddtool.exe` / `_internal/` / `data/` / `version.txt`
> 多套一层（如 zip 里是 `zzz-ddtool/xxx`）会导致解压错位。脚本已按此产出并有测试钉住；若绕过脚本手工打 zip，这条要自己保证。

### 构建输出保护

`build.py` 在**任何清理、建目录、写入和打包调用之前**先验证路径，不通过就打印原因、以退出码 2 结束，不改动磁盘上的任何文件：

- 目标包目录不得与源码内的固定目录重叠——`.git`、`.venv`、`src`、`tests`、`scripts`、`data`、`user`、`log`、`log_test`、`docs`、`dev-docs`、`build`——也不得与**源码根同级的 `dev-docs/`** 重叠。两个方向都拒绝：包目标落进这些目录，或包目标把这些目录包含进来。
- 同级目录按「源码根的同级」这一相对关系定位，不写死本机路径、不读取其中内容、也不要求它存在：源码根整体搬家后保护自动跟到新位置；公开项目没有 `dev-docs/` 时，正常的外部输出照常可用。
- 目标包目录不得包含源码仓库，也不得经链接转向其他位置；`build/` 中间目录同样按实际路径校验。
- 清理目标必须是目录；其中出现 `.git`、`.zzz-ddtool-root`、`pyproject.toml` 或 `user` 标记时拒绝删除。

误填 `--outdir ..` 会在这一层被拒绝并保留文件。

## 3. 传到 GitHub 发行版

仓库：`tim883/zzz-ddtool`；**必须保持公开**，否则发行版 API 匿名读不到，而程序按设计不带 token 访问。改账号或仓库名时，改 `src/zzz_ddtool/updater.py` 顶部的 `GITHUB_REPO` / `GITHUB_BRANCH` 两行即可（示例清单直链也由它们拼出）。

**单个附件上限 2 GB**，`_internal/` 较大的程序包可整包上传；不需要再为体积拆包。

**网页操作**（推荐，简单）：

1. 打开仓库 → 右侧「发行版 / Releases」→「新建发行版」。
2. 填 **标签（tag）= 版本号**，如 `v0.2.0`（带不带 `v` 都行，程序会自动去掉）。
3. 填标题 + **更新说明**（这个说明会原样显示给用户看，写清楚改了什么）。
4. 上传上一步的 zip 附件。
5. 发布。

发布流程 3 步：

1. 打 zip；
2. 传发行版附件；
3. 填版本号 + 说明。

## 4. 用户侧更新时发生什么

| 情形 | 用户看到 | 程序行为 |
|---|---|---|
| 有程序包 | "发现新版本 X，现在更新？" | 下载 → 退出 → 替身 bat 覆盖 → 重启新 exe |
| 只有数据包 | "发现新版本 X，现在更新？" | 下载 → 覆盖 `data/` → **立即生效、不重启** |
| 已是最新 | "已是最新版本 X" | 无动作 |
| 无网络 / 无发行版 | 对应错误提示 | 无动作 |

数据更新覆盖 `data/`；程序更新覆盖程序目录中的包内文件。本流程的发布包不包含 `user/`，存档位置见 [开发与运行](开发与运行.md)。**日志与 `user/` 同一条定位规则，落在公共根 `log/`，不在版本目录内**——换版本目录不会丢掉旧日志。当前更新器没有覆盖前备份或失败回滚。**更新器另有一层剥离**：解压后、覆盖前会删掉更新包里顶层的 `user/`、`log/` 与 `log_test/`，即使发布包出了错，用户侧也不会被覆盖。

## 5. 端到端验证（发版后自查）

1. 拿**上一个版本**的 exe（或把 `version.txt` 临时改小）。
2. 点「检查更新」→ 应提示新版本 → 确认。
3. 数据更新：确认 `data/` 被覆盖（同名文件覆盖，多出来的旧文件不会删除，不是整体替换）、`user/plan/` 与 `user/last-config.json` 没动。
4. 程序更新：确认退出后自动重启、**页头版本号变成新的**、`_update.bat` 已自删。

## 6. 未完成 / 风险（发版前必读）

- **打包态任务未验**：exe 内实际任务、F9/F10 和停止按钮仍待覆盖；另一台电脑与干净 Windows 验证也尚未完成。
- **`.bak` 自动回滚未实现**：`apply_program_update` 现在是直接 `xcopy` 覆盖，没有"覆盖前备份、失败回滚"。
- **替身脚本的路径必须走参数，不能写进正文**（2026-10-14 真机首次更新时定位并修复）：脚本正文含安装路径时，`encoding="ascii"` 会因中文路径抛 `UnicodeEncodeError`，而 `Path.write_text` 是**先建文件再编码**，于是留下一个 **0 字节的 `_update.bat`**，更新静默失败。改成 `encoding="mbcs"` 是假解——脚本写得出来，但 cmd 按自己的代码页读，`xcopy` 一条都复制不到（已在全中文路径下实测）。现行写法：正文保持纯 ASCII，两个路径经 `%~1`/`%~2` 由命令行传入（走 `CreateProcessW`，与代码页无关）。回归用例 `test_update_bat_survives_non_ascii_install_path` 钉住这条，并已反向验证会因旧写法变红。
- **更新失败必须弹窗**：原先失败只在状态栏写一行小字；下载 139 MB 耗时长，用户会把失败当成「卡住」（2026-10-14 线上就是这个表现）。现除状态栏外再弹 `QMessageBox.warning`。
- **在线更新已在真机跑通**（2026-10-14，v1.0.1）：完整链路（检查更新 → 提示新版本 → 下载 → 退出 → 替身脚本替换 → 自动重启）在**中文安装路径**下端到端验证通过——正是 v1.0.0 首次执行失败的那个条件，即上面那条编码缺陷的最终复核。当时的判据：`version.txt` 由 0.9.0 变为 1.0.1；程序目录内的 exe 与发布包字节数一致，且从它里面解出的 PYZ 含当版新增代码；`_update.bat` 已自删；新进程的启动时刻晚于替换时刻；日志开出新一轮。**在此之前，更新器从未在真机跑通过一次。**
- **下载进度已随 v1.0.2 交付**（2026-10-14）：程序包约 140 MB，原先状态行只有一句「正在下载程序更新…」，用户无法区分「慢」和「卡死」——两次实机复验都被误判成卡住。现 `updater._download` 改为分块读并回调 `progress(已下载字节, 总字节或 None)`，状态行显示「百分比（已下载 / 总量），约剩 N 分钟」；总量取不到（分块传输）时退化为「已下载 N MB」。进度**必须经 Qt 信号跨回主线程**，工作线程不能直接改控件。`operation` 是否需要该回调用 `inspect.signature` 判断，零参操作（检查更新、取示例、生成组合）照旧。回归用例 `test_download_reports_progress_with_content_length`、`test_download_progress_tolerates_unknown_total`、`test_utility_progress_line_shows_percent_and_size`，已反向验证：短路进度回调即变红。**自 v1.0.2 起随程序包发布。**
- **套装图不属于发布前置项**：`assets/sets/` 的图片既不在 `pyproject.toml` 的 `package-data` 也不在 `zzz-ddtool.spec` 的 `datas` 里，所以打包产物不带这些图。界面按两条路径走：图片存在且可解码时用图片，缺图时用完整套装名文字 + 计算色块；源码态仓库内有图，走的通常是前者。
- **下载渠道**：正式发布时核实附件可下载。
- **匿名 API 限流 60 次/小时/IP**：GitHub 对未认证请求（含发行版列表）按出口 IP 限流。校园网、小区宽带、公司等共享出口可能被一起打满；程序对 `403 + 配额耗尽` 有专门提示，但没有退避重试。
- **`latest` 按 `created_at` 排序，不按版本号**：GitHub 的 `created_at` 取该发行版**所用提交的日期**，不是发布时刻。先发新版、过几天再给旧版补热修时顺序会反过来，补发的那版不会被识别为更新。

## 7. 更新公共示例（不用发版）

示例与清单直接放在本仓库 `data/examples/`，用户从界面「获取公共示例」按需下载。

```powershell
# 改完 data/examples/ 里的示例后，一条命令完成：生成清单 → 入库 → 推送
.\.venv\Scripts\python.exe scripts\release.py examples
```

- **生成清单不是独立动作，而是发布流程的固定步骤**——`release.py` 每次都跑它，控制 `data/examples/` 就等于控制发版，不存在"忘了重生成清单"的窗口。
- `examples` 场景只推仓库、不打包，因此不强制要求工作区干净（只提醒）；`program` / `data` 会硬性拦截。
- 清单里的 `note` 是界面上显示的说明，**手写，重新生成时按文件名保留**。
- 用户侧会逐个核对 `sha256`，与清单不符的一律拒绝落盘。
- **示例文件名优先用纯 ASCII**：文件名会拼进下载地址，而 v1.0.2 之前的客户端不做百分号编码——中文名在**下载那一步**失败（清单仍取得到，示例一份都下不来，2026-10-14 实测 `UnicodeEncodeError`）。v1.0.2 起客户端会先编码，但旧版用户仍在线上，取不到就得先更新程序。界面上显示的中文标题来自 YAML 顶层的 `name`，**与文件名无关**，所以中文标题 + ASCII 文件名是推荐组合。
- 改了示例**不必**重打程序包，也不必发发行版 —— 推一下仓库即可。

## 8. 对照：改动 → 发什么包

| 你改了什么 | 发哪个包 | 用户侧动作 |
|---|---|---|
| 套装名 / 词条名 | 数据包（`data/` 的内容，体积以当次产物为准） | 点更新 → 立即生效 |
| 任何代码 / 内置模板资源 | 程序包（大小以当次产物为准） | 点更新 → 退出重启 |
| 公共示例（`data/examples/`） | 不发包，`release.py examples` 推仓库 | 「获取公共示例」按需下载 |
