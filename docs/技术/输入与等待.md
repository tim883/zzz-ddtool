# 输入与等待

本文维护点击与滚轮协议、释放后等待与就绪下限、停止与中断边界。坐标基准与设计分辨率见 [截图与坐标](截图与坐标.md)，识别判据与阈值见 [识别标定](识别标定.md)，页面判读见 [页面识别](页面识别.md)。

## 一、两层等待

一次动作的时间由两层叠加而成：

1. **输入层**：`wininput` 发完输入后自己收尾等待。五类输入的收尾是固定值（毫秒）：`click_client` 180、`wheel_client` 330、`press_key_once` 580、`press_key` 650、`send_wheel_event` 0。这些值是旧收尾请求的保守上界，不是测量值。
2. **动作层**：调用方从**真实释放时刻**起，按该动作的下限分片睡满。真实释放时刻取 `InputRelease.released_at_ns`——早于收尾等待、日志、抓图和观察回调；分片请求不超过 20 ms，片前后检查停止/暂停。下限到达不等于业务就绪，业务就绪另由就绪等待判定。

调用方用 `input_context(..., defer_post_release=True)` 接管时，输入层不再收尾，动作层下限就是该动作唯一的释放后等待。筛选类动作的最终等待写成「实测值 + `_MEASURED_SAFETY_MS`（200 ms）」，保底量只在 `_MEASURED_SAFETY_MS` 一处定义，不再往数值里另加固定量；`set_scroll` 用已含余量的最终预算 784 ms，不再叠加。

## 二、输入内部的固定值与区间

释放前的时序是固定值与区间混用（`pause` 用 `uniform` 取样）：

| 输入 | 释放前 | 释放后（输入层收尾） |
| --- | --- | --- |
| `click_client` | 光标移动到目标后 40—80 ms → 左键按下 → 80 ms → 抬起；Alt 组合在按下前按住 Alt 150—220 ms，抬起后 40—80 ms 释放 Alt | 180 ms |
| `wheel_client` | 移光标后 40—80 ms → 单条 `delta×120` 原始事件 | 330 ms |
| `press_key_once` | 一对 down/up，中间 50 ms | 580 ms |
| `press_key` | 多通道发键，组间 40 ms、30 ms | 650 ms |
| `send_wheel_event` | 只发一条原始滚轮事件，不聚焦、不移光标 | 0 |

`focus_window` 每次先聚焦并等 200 ms，未成功再执行一轮并等 200 ms；仍不在前台则报错（按键会点到别的窗口）。这些区间是代码常数，没有证明是游戏的最低需要时间。

## 三、六类就绪等待

[readiness.py](../../src/zzz_ddtool/readiness.py) 的六类等待从输入函数正常返回后计时：poll 固定 50 ms、连续稳定 2 帧。

| kind | 生产下限 ms | 无兜底时的默认下限 ms | 超时 ms |
| --- | ---: | ---: | ---: |
| `select_disc` | 520 | 500 | 3180 |
| `open_preview` | 800 | 900 | 5180 |
| `open_upgrade` | 527 | 1500 | 8180 |
| `material_ready` | 947 | 600 | 3180 |
| `upgrade_result` | 550 | 1500 | 8180 |
| `return_warehouse` | 300 / 680（逐边），动作级兜底 1611 | 600 | 3580 |

- 三个数值各有来源：**生产下限** = 真机实测值 + 200 ms 保险余量，由 [runner.py](../../src/zzz_ddtool/runner.py) 作为动作级兜底传入；**无兜底时的默认下限** 是 `readiness` 自己的默认值，只在标定、档案校验这类不经过 runner 的路径使用；**超时**取固定表值。下限与超时都按释放时刻起的活动时间计（扣暂停），下限之后不重开超时。
- `readiness` 自己的默认超时与它的默认下限成对出现（依次为 3000 / 5000 / 8000 / 3000 / 8000 / 3000 ms），同样只在不经过 runner 的路径生效。
- `refund_confirm` 与 `refund_dismiss` 同为实测值 + 200 ms（1277+200），超时 8180；R/T 类标签动作共用 135+200 = 335 ms。
- 本机等待档案可以按 kind 调整下限：`user/post-release-waits.json` 里 floor 必须严格小于对应超时，越界的项只按该项缺项处理、不牵连其他动作，其余字段非法才整档失效；`user/scan-waits.json` 里任一项不合法（含 `timeout_ms ≤ min_wait_ms`）就整份失效、全部回落到默认值。

下限的计算口径有两处，公式不同：

| 档案 | 模块 | 公式（M = 有效样本的最大稳定用时） | 最少样本 |
| --- | --- | --- | ---: |
| `user/post-release-waits.json` | `actionwait.py` | `ceil((M + max(20, ceil(M×0.10))) / 10) × 10` | 动作级 10；逐边 5 |
| `user/scan-waits.json` | `readiness.py` | `ceil((M + max(20, 2×poll_ms)) / 10) × 10`，poll=50 ms 时即 M+100 向上取整到 10 | — |

`predicate_version` 当前为 2，与档案件里的 `schema_version` 一起参与装载校验；不匹配时整档失效、全部回落到默认值。逐边档案写在根字段 `return_edges`（`schema_version=2` 新增），键只能是两条允许边（`modal_preview` / `preview_warehouse`）。

## 四、批量点击：组内零等待，只等最后一次

同一批目标（套装选项、主属性选项、副属性词条与数量）**先用一帧准备整批**，再连续点击：

- 组内相邻点击之间等待为 0，且不在点击之间抓图判读；切换动画只由后续帧观察。
- **只有最后一个实际点击**按其动作的实测等待收尾：`set_option` 87 ms、`mainstat_option` 160 ms、`substat_option` 93 ms、`substat_count` 86 ms。
- 一批里没有实际点击时不等待；末尾暂态只观察新帧、不补点击，观察后仍与期望不符才报错。
- 输入前检查分两档：**无缓存的学习/首次路径**在整批点击前检查弹窗布局与目标身份，并在底层检查点返回后复验；暂停恢复后只复验剩余未点目标，已完成的点击不重发。**缓存回放**只核对窗口绑定（句柄、进程、客户区尺寸、DPI），不截图、不识别页面。

滚动类等待另按动作计算（见第五节），不与点击的收尾等待混用。

## 五、滚轮协议：出厂默认值，启动不标定

| 值 | 默认 | 含义 |
| --- | ---: | --- |
| `events_per_row` | 1 | 1 条滚轮事件 = 1 行 |
| `row_pitch_px` | 175 | 行距 |
| `event_interval_ms` | 100 | 相邻事件间隔 |
| `settle_wait_ms` | 100 | 滚动后等画面停稳 |

滚动按行、不随筛选或列表长短变化，属**游戏规则常数**，所以开局直接用出厂默认值，不必每次启动重新标定。用户档案 `user/navigation-profile.json` 命中时优先使用；缺档、坏档或环境不匹配一律回落到出厂默认值，启动直接进筛选页。`_ensure_profile(hwnd, recalibrate=True)` 保留为**显式重标定入口**（游戏更新改了滚动行为时用），只有那条路径才做「重置筛选 → 标定」。`origin_center_y` 不在默认值之列：它是「第 1 行图标中心的屏幕 y」，随当前滚到哪而变，每个任务开头按当前画面重新量，写死必然错位。

协议常量与用法：

- `wheel_client(delta=-3)`：一次缩放后的单条事件（-3 格 = -360 原始单位，一格固定 120）。实测一次 -3 约 200 px、屏内行距约 150 px（≈1.3 行）；方向由原始事件符号决定，负数向下、正数向上。
- 批量按行滚动用 `send_wheel_event`：只发一条原始滚轮事件，不聚焦、不移光标、零内部等待；调用方按 `event_interval_ms` 在事件之间自己等待。**不要用一条放大的 delta 代替已标定的多事件序列**——游戏可能对单条大事件限幅或合并。
- 套装弹窗列表按单条事件 `-8`（原始 -960）步进，实测约 447 px、约三行；底部由游戏截断，保留重叠行。
- 弹窗内没有可见滚动条：顶部判定只能靠可见内容与顶部锚点，不能用滑块。

### 面板滚到底与底部点击禁区

筛选面板内容比视口高（「主属性词条」区默认在视口外），滚轮落点为面板中部 `(1560, 500)`。

- 面板最下方有一条固定高度的**点击无效带**：实测按钮中心 y=942 点不动、y=901 能点、副属性「展开」按钮中心 y=916 点不动，即中心 y≳910 一律无效。面板内任何目标**底边低于 `height-160`** 时必须先滚动把它顶上来再点，不能点了没反应再补救（那样必然失败）。
- 要一次到底时连发 8 条滚轮事件：实测一格约 41 px、内容比视口高约 300 px，到顶后会停住，多发无害。宁可一次发到位，也不要「滚一格 → 抓图 → 再滚」。
- 副属性词条刚展开、面板未滚动时只露出部分词条，其余在可视区外（目标缺失态）。此时先一次滑到底再定位，首帧之后再观察最多 3 次；仍不就位则中断并列出缺失项，不选择部分属性。
- 滚动找词条的尝试上限是 8 轮；把面板滚到主属性区的尝试上限是 8 次（实测 3~4 次即到底）。

## 六、「阶段添加」→「升级」的固定间隔

[runner.py](../../src/zzz_ddtool/runner.py) 在素材输入（点「阶段添加」）之后只等一个固定间隔 `_STAGE_ADD_TO_UPGRADE_S = 0.1 s` 就点「升级」：

- 阶段添加后到点「升级」的间隔取 **0.1 s（保险余量）**，上限要求 **≤500 ms**。
- 阶段添加后的动画不必等画面稳定：直接点「升级」会让动画立刻结束，结果一样；素材是否到位也不在这一步确认——点下去没反应会在后面的 `upgrade_result`（8180 ms 预算）里超时暴露。
- 「升级」不抓帧、不 OCR 找文字，直接点设计坐标 `UPGRADE_BUTTON_CENTER=(1511,866)`（经 `scale_point` 缩放），写法与「》」箭头用固定点一致。
- `material_ready` 这个动作 ID、它的探针与像素阈值**保留**：`_pick_material`（`material_slot>0` 的测试入口）仍消费它，生产路径已不触发。

## 七、切页置顶：认页驱动，无固定等待

[nav.py](../../src/zzz_ddtool/nav.py) 的 `_switch_tab` 点完页签**立刻抓图认页**，认不出就继续重拍：同一页签最多点 2 次，每次点击后的认页最多取 `max(1, ocr_retry)` 张（含首次）；仍认不出才存现场图并抛 `NavError`，不盲点更多次。

切页成功那一刻即返回，动画未完成时由后续帧或下一次点击收敛。这是页签切换的**就绪判据**，不是释放后等待，因此不进六类下限表；`reset_to_top` 也因此没有固定等待。

## 八、`return_warehouse` 逐边下限

`_esc_back_to_grid` 每次按 Esc 之前先认层，并按这次所在的边取等待下限——两条允许边各自一个值、互不牵连：

| 边 | 语义 | 运行时常量 ms |
| --- | --- | ---: |
| `modal_preview` | 弹层 → 缩放预览层 | 300 |
| `preview_warehouse` | 缩放预览层 → 仓库 | 680 |

- `modal_preview` 是 2026-10-13 用户裁定改的：该边取 **100（实测）+ 200（`_MEASURED_SAFETY_MS`）= 300 ms**，旧值 1680 ms 偏长。`preview_warehouse` 沿用原运行期兜底 680 ms。
- 同日删掉原第三条边名 `modal_warehouse`（弹层 → 仓库）：边名只按**发键前**那层取，这个名字生产路径永远选不到，留着还会让逐边标定永远凑不齐全部边。转移本身仍算完成——游戏若一脚从弹层退到仓库，那一帧判层照常认成仓库、等待照常结束，只是没有独立边名与独立下限，按 `modal_preview` 取值。
- 常量是**运行期兜底**，来自运行时证据而非按 Spec 口径做的逐边真机实测（每边 ≥5 个有效样本后由档案的 `return_edges` 覆盖）。取不到实测就回落到动作级兜底 1611 ms，不借用别的边的值。
- 逐边取值让第 0 帧就 ready 的快边不再被慢边拖住。
- 判层判据、探针边判定、3580 ms 超时、两帧稳定与 50 ms poll 都保持不变。中间 preview 只结束本次 Esc 等待，严格确认 warehouse 才结束返回；同层或 unknown 不完成本次等待、不加计数。
- `readiness.summarize_return_warehouse` 仍是标定与门禁侧的逐边汇总（取各边最大值，缺边不算标定完成）。

## 九、筛选面板打开与「重置」的重开边界

漏斗按钮（`FILTER_BTN`）是**开/关切换**。面板本来就开着时（上一轮没关就点了开始），开头那一下会把它关掉，接着找「重置」读空、整轮中断。

`_open_panel_and_reset()` 的做法（上限常量 `_RESET_TRIES = 4`）：

1. 点一次漏斗 → 等 `open_panel` 下限 → 找「重置」（`FILTER_RESET_AREA=(1250,990,1650,1080)` 内读「重置」，避开右侧「批量操作」）；
2. **读不到就再点一次漏斗重来**，总共最多 **4 次**（首次 + 最多 3 次补点）——开关按偶数次回到原状态，补点能把原本开着的面板恢复，原本关着则第一次就已经打开；每次补点记一条日志，写明这是第几次；
3. 试满 4 次仍未读到才抛 `FilterClickError`，中断整轮。

代价：面板本来关着（正常路径）仍是点 1 次漏斗 + 读 1 次区域 OCR，**不额外抓帧**；面板本来开着时多 1 次点击 + 1 次区域 OCR，把必然失败救成正常继续；真机偶发「补点一次仍读空」时，后面几次还能垫底。判断**只用「读没读到重置」，不读亮度、不判面板开没开**，不依赖跨机器会变的像素阈值。`reset_game_filter` 传 `allow_reopen=False`：它读不到时紧接着就 Esc 关面板，没有「再点重置」的下一步，补点没有意义，只试首次。

## 十、停止、暂停与中断边界

- F9 暂停 / F10 停止与界面按钮共用同一控制器；检查点在**业务检查点与下一次输入动作之前**生效，导航、标定、筛选和强化途中都会响应。
- 等待分片每片请求不超过 20 ms，片前后各检查一次停止/暂停，所以暂停与停止在等待期间也能及时生效。
- **暂停不计入下限与超时**：下限与超时都按活动时间计，从释放时刻起扣除实际暂停区间；暂停代次改变会丢弃旧帧、连续计数、返回候选与最后样本（恢复后仍须两帧新证据），但**不重开下限预算**。
- `material_refund` 是唯一的受控中断：需两个独立稳定候选才抛 `ReadinessInterrupted`，且只允许用于 `upgrade_result`。
- 正在执行的 OCR、等待和一次完整点击/按键会先结束，避免留下未释放的键；停止后保留当前游戏页面供复核。
- 标签复核（R/T）：输入返回后每次先等 50 ms，最多 `max(1, preset.ocr_retry) × 4` 次；只在新帧上重读，**不补按**。另一标签状态意外改变或一直未知时失败并停止任务链；弃置锁定盘先 T 确认解锁再 R。
- 输入观察（`capture_inputs`）用 ContextVar 隔离，真实 begin/end 共享 `call_id`，每行 17 个字段：`t_ns`、`event`、`call_id`、`api`、`role`、`target`、`stage_index`、`selected`、`hwnd`、`x`、`y`、`alt`、`vk`、`delta_units`、`status`、`error`、`released_at_ns`；初始检查点停止时不分配调用 ID。**输入结束事件在函数收尾等待之后记录，不能把 end 当作真实释放时刻**。

## 十一、验证边界

上表的生产下限、逐边常量与固定间隔都来自本机运行期证据与真机实测。逐边常量只是运行期兜底，不是逐边实测值；换机器、换游戏版本或改动画表现后需要在本机重新核对，离线回归不能替代真机点击验收。滚轮事件间隔由调用方按 `event_interval_ms` 负责，跨版本是否仍适用同样需要实测。
