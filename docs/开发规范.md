# 开发规范

更新：2026-10-13。适用于本仓库及协作 agent。**现行规范、功能说明与使用/技术文档维护在 `docs/`；在研与历史开发资料维护在源码根同级的私有目录（相对源码根写作 `../dev-docs/`），只供本地开发，不随公开仓库提交。**

## 1. 固定入口和存放位置

| 内容 | 唯一维护位置 |
| --- | --- |
| 文档总入口 / agent 自动发现入口 | [文档索引](./README.md) / 仓库根 `AGENTS.md` |
| 项目开发规范 | 本文；不在多个目录维护全文副本 |
| 稳定的游戏前提 | [游戏规则](./游戏规则.md) |
| 用户怎么操作现有工具 | `docs/使用/` |
| 已实现的技术机制、坐标和识别方法 | `docs/技术/` |
| 程序实际加载的识别模板 | `src/zzz_ddtool/assets/`，属于运行资源 |
| 回归专用输入 | `tests/fixtures/`；长期有效的测试截图按页面建子目录，跨页面共用的样本直接放 `tests/fixtures/` 根 |
| 当次运行日志 / 临时探测图 | 正式运行写 `log/`，测试与开发脚本写 `log_test/`；两者都不进 git，都按轮数策略清理 |
| 用户任务存档 | `user/plan/`；不放 AppData，不随版本包搬迁 |
| 在研 / 搁置方案与历史资料 | 源码根同级的 `../dev-docs/`，本地开发资料，不随公开仓库提交 |

资料分工：`docs/` 维护现行规范、功能、用法与技术知识，源码根同级的 `../dev-docs/` 保存开发方案与过程资料；改造落地后及时把现行知识整理进 `docs/` 对应页面。

这两个位置都供开发者使用，不是按“用户文档 / 开发者文档”拆分：发布流程是持续使用的操作说明，放在 `docs/技术/`。`../dev-docs/` 按“源码根的同级目录”这一相对关系定位，源码根整体搬家后它跟着走；公开项目没有这个目录，也不影响 `docs/` 与构建。它是私有资料，公开文档只说明它的存在与用途，不引用其中文件的具体路径。

根 `README.md` 是项目首页，详细文档只有一套，不要把同一段项目介绍复制到各级 README。

## 2. 图片与样本

写代码时引用的画面样本必须能解释游戏语义：对应哪个页面 / 状态、什么条件下截取、画面元素意味着什么、操作之后会发生什么、这些规则如何影响实现。动态机制不能从单张静态图推出；无法从单图判断时引用 [游戏规则](./游戏规则.md) 中已记录的条款，不临时编造。

运行图与长期样本不能混用生命周期。运行图是某轮任务的步骤或故障证据，落在该轮目录 `log/<时间戳编号>/captures/`（测试与开发脚本在 `log_test/` 下同构存放），可能被轮数策略回收；写代码时可反复引用的长期样本放 `tests/fixtures/`，纳入源码版本管理，不参加日志清理，也不作为用户运行包资源。

- 文档配图优先引用 `src/zzz_ddtool/assets/` 中程序实际加载的同一文件，或 `tests/fixtures/` 中已有的样本，不复制第二份。
- 需要新样本时只采集本次涉及、足以解释行为的量，不把每轮运行图灌入样本目录，也不为已完成且不改动的功能追补图片。
- 样本按客户区实际图像保存，PNG 无损；1920×1080 是设计坐标基准，不拉伸历史图冒充原生。
- 没有采集日期、DPI 等历史元数据时标“未记录”，不能据此把已完成功能重新列为阻塞待办。

## 3. 文档维护流程

- 开工前读本文、[游戏规则](./游戏规则.md)，以及 `docs/技术/` 中对应的现行说明。已稳定的游戏前提直接使用；只有新证据与已记录条款冲突时，才指出冲突并讨论修订。
- 实现期间同步修订 `docs/` 中的现行说明；在研方案与未完成事项写在 `../dev-docs/`，`docs/` 不写尚未实施的设计。
- 行为落地后把现行行为、命令与数据口径整理进 `docs/` 对应页面，并核对受影响的链接与输入路径。
- **重复性操作必须成文**：需要多次执行、或产物必须保持一致的操作（样本采集与裁剪、资产登记、验证步骤）必须写成 `docs/` 对应页面的规范条款，不能只存在于临时脚本或单次会话记录；**实现手段可以不同，产物口径必须一致**。
- 文档只写当前可核实的现状：不写版本演变、历史修改说明、会话与审查过程，也不写运行编号和通过数量。测试数量与环境信息只代表对应日期，不自动变成今日事实。

测试的唯一现行约定见 [测试约定](./测试约定.md)：按改动与调用链选测，只有影响面广、共享契约变化或明确发布要求时才说明理由并扩大范围；已通过且没有新增改动或具体疑点时不重复运行。

## 4. 开发约束

- 本地截图 / OCR / 模拟输入；弃置仅打标，不分解、不读游戏内存、不改游戏文件、不抓包。
- 强化按每 +3 档重新判断；初始 3 / 4 词区分处理。任务 `accepted=None` 表示未生成而跳过；空白名单 `[]` 是有效配置，该任务不再回退到权重接受。
- F9 暂停 / 恢复、F10 停止与 GUI 共用控制器，在安全检查点生效；任务后台执行、界面保持响应，关闭窗口先请求停止。未知情况无法可靠继续时有限重试后停止整条链，失败不能显示完成。
- 列表定位按批复用，不为补样本改成每盘重扫、每行截图。仓库位置、端点与恢复判定完全不用滑块，包括辅助和兜底路径。
- 开发 / 打包目标 Python **3.13.5**，显式使用项目 `.venv\Scripts\python.exe` 和 `requirements-lock.txt` 锁定依赖；包元数据的 `>=3.11` 不是可以混用解释器与依赖版本的约定。解释器、系统 DPI 和滚轮协议必须本机核实，不凭历史文档修改全局环境。
- `build.py` 的打包输出保护拒绝把包目标落在源码内 `docs/`、源码根同级 `../dev-docs/`（含其子目录）或包含这些目录的位置；该保护按源码根的相对关系定位，源码根搬家后自动跟随，公开项目没有该同级目录时正常输出仍可用。细节见 [打包与发布](./技术/打包与发布.md)。
- 目录整理保留图片内容、运行模板、既有功能与用户存档；需要打包时另行执行打包流程并保留旧包。
